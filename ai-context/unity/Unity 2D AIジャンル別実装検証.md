# Unity 2D AIジャンル別実装検証

Unity MCP + Claude Code (Opus 4.6) で3種類の2Dゲームを実装した実証実験。ジャンルによってAIの成功/失敗パターンが大きく異なる。

---

## 検証概要 (dev.classmethod.jp)

**環境**: Unity MCP + Claude Code (Opus 4.6)  
**プロンプト構成**: 内容要件 + 品質仕様 + 制約 (外部アセット禁止、即時プレイアブル)

---

## ジャンル1: 弾幕シューティング (成功)

**所要時間**: 7.5分  
**結果**: 初回出力で即動作

5種類の弾幕パターンを実装し、即座に機能した。追加プロンプトで「画面上に500-1,000発の弾を同時表示」を要求したところ、Claudeが自律的に最適化:

- **オブジェクトプーリング**: 1,500発を事前割り当て
- **物理計算の廃止**: 手動距離チェックに切り替え
- フレームドロップなしで性能を維持

**なぜ成功したか**: ルールが明確 (弾を避ける)。データ整合性 = プレイアブル性が一致する。

---

## ジャンル2: 自動生成プラットフォーマー (成功)

**所要時間**: 9分  
**結果**: 初回出力でほぼ機能

横スクロールで足場を自動生成。初回から「ゲームとして成立」した状態で出力された。

**軽微な問題**: 足場配置のビジュアル調整が必要 (スクリーンショット解析で修正)

---

## ジャンル3: 探索ダンジョン (部分的失敗)

**所要時間**: 49分 (計画18分 + 実装/テスト31分)  
**結果**: 初回出力でプレイ不能 → 修正後も問題残存

### 失敗パターン1: 初期スポーンの詰み

「スタートルームに高い障害物が生成され、別の部屋にあるダブルジャンプ能力なしでは越えられない」

### 失敗パターン2: 脱出不能ルーム

「上方向のみに通路があるルームに落下すると、ダブルジャンプなしでは脱出不能」

### 根本原因

**データ整合性 ≠ 体験整合性**

Claudeは「ロジックとして正しい能力配置」を検証したが、「現在の能力で実際に到達できるか」を検証していなかった。テスト方法がMCP経由でのプレイヤーワープであり、キーボード操作による実際のプレイではなかった。

### Claudeが自律修正できた範囲

7回の独立テストを実行し、5つの問題を修正:
- コンソールログによるUI確認
- スクリーンショットによる足場配置確認
- 状態クエリ (部屋分布、プレイヤー位置)
- PlayMode中の挙動観察

### 修正プロンプト例

```
「スタートルームから出られません。
初期能力のみで隣の部屋に移動できるよう修正してください」
```

## 2D パスファインディングの現状

Unityは標準でNavMeshが**2D非対応** (3D専用)。AI生成コードで2D敵AIを実装する場合の選択肢:

| 方式 | 難易度 | AI対応 | 備考 |
|------|--------|--------|------|
| Waypoint巡回 | 低 | 優秀 | 固定ルートのみ |
| NavMesh Plus (サードパーティ) | 中 | 中 | 追加パッケージ必要 |
| A*自前実装 | 高 | 可能だが複雑 | パフォーマンス注意 |
| A* Pathfinding Project (有料) | 中 | 良好 | 参照文書必要 |

AI生成コードでのパスファインディング注意点:
- NavMeshは3D前提のコードを生成することがある → CLAUDE.mdに明記必要
- 複雑なA*実装はClaude生成コードでバグが出やすい
- waypoint巡回は確実に機能する (事例多数)

## ジャンル別 AIとの相性マトリクス

| ジャンル | AI成功率 | 主な課題 | 人間の補完領域 |
|---------|---------|---------|--------------|
| 弾幕シューティング | 高 | なし | ゲームバランス調整 |
| 横スクロールプラットフォーマー | 高 | 足場配置調整 | ビジュアルポリッシュ |
| ローグライク (手続きダンジョン) | 中 | プレイアブル性検証 | トラバーサル確認 |
| パズルゲーム | 中 | 解法の一意性 | 難易度設計 |
| RPG (複雑なゲームフロー) | 低-中 | 状態機械の複雑さ | 全体フロー管理 |

## 教訓: 効果的なプロンプト設計

1. **プレイアブル性を明示**: 「初期能力のみで全ルームに到達可能であることを確認してください」
2. **数値制約を指定**: 「ジャンプ高さ=2タイル、初期能力=ダッシュのみ」
3. **体験テストを要求**: 「キーボード入力を想定して実際の動線を検証してください」
4. **段階的な複雑度**: 簡単なルームから始めて段階的に複雑にする

## AI Grimoire での実戦評価

| 評価軸 | 評価 | 備考 |
|--------|------|------|
| **実戦投入レベル** | **必読** | AI Grimoireはローグライク要素を含む。「データ整合性 ≠ 体験整合性」の教訓は直接適用可能 |
| **MVP必須度** | 高 | どのジャンルの罠に入るかを事前に知ることでハッカソン時間を節約できる |
| **AI実装適性** | — (参照用) | |
| **人間が実装すべき箇所** | 「ゲームとして面白いか」の判断。AIはデータ整合性は確認できるが体験は確認できない |

**AI Grimoire への直接適用**:
- 音声評価の「数値的正確さ」と「詠唱体験の面白さ」を別軸でテストする
- `spell_power` が数式的に正しくても、実際に詠唱して「強くなった感」があるか確認する
- ダンジョン生成は MVP スコープ外（固定1フロアで十分）
