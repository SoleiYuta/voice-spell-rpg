# リスクと対策

---

## リスク一覧

### リスク1：不適切な方向に寄りすぎる

**内容：** AIが下ネタや不快表現を含む呪文を生成してしまう。審査・配信環境では致命的。

**対策：**
- 審査提出版の呪文カテゴリを以下に限定する
  - 厨二病セリフ（例：「我が右手の覇王を解放せよ！」）
  - 早口言葉（例：「赤パジャマ青パジャマ黄パジャマ、三回言え！」）
  - 熱血セリフ（例：「俺の魂が、お前に届けてみせる！」）
  - ポエム調（例：「闇に咲く薔薇よ、その散り際を我に見せよ」）
- Geminiプロンプトに明示的な制約を入れる
  - 「性的表現・暴力表現・差別表現を含む出力は禁止」
  - 「全年齢向けのエンターテインメントとして適切な範囲で生成せよ」
- 出力フィルタリングを実装（NGワードリスト）

---

### リスク2：ゲームを作り込みすぎてAI部分が弱くなる

**内容：** 見た目や演出に時間をかけすぎ、AIエージェントがダミーに近い状態でデモを迎えてしまう。

**対策：**
- 開発優先順位を「AIが動くこと」に固定する（[[06_MVP開発計画]] 参照）
- ゲームのグラフィックは仮素材・フリー素材で固定
- ゲーム部分に追加機能を入れるのは「AIが正常に動作している」確認後のみ
- チェックポイントを設ける：「Geminiが呪文を返してくるか？」を最初に確認

---

### リスク3：音声認識精度が不安定

**内容：** 環境ノイズ・マイク品質・滑舌によって認識率が大きく変わる。完全一致を前提にすると失敗が頻発する。

**対策：**
- 完全一致評価を廃止。以下の指標で評価する
  - 発音一致率（部分一致・類似度スコア）
  - キーワード認識率（重要単語だけを検出）
  - 詠唱完了率（最後まで読んだか）
- 認識失敗そのものをゲームの「失敗演出」として活用
- バックアップとして「テキスト入力モード」を隠し機能として実装
- デモ環境はできる限りノイズの少ない環境を確保

---

### リスク4：デモで伝わりにくい

**内容：** AIが適応しているように見えず、「ただの音声入力ゲーム」と思われる。

**対策：**
- AIの判断コメント（「君は大声が得意だ」）を画面上に大きく表示
- 1回目と2回目の呪文が違うことを発表者が口頭で強調
- デモ前に「AIがリアルタイムで判断します」と宣言する
- 30秒シナリオを事前に練習し、AI適応の瞬間を必ず見せる構成にする
- 詳細は [[07_発表デモ構成]] 参照

---

### リスク5：ハッカソン要件とズレる

**内容：** DevOps要素やGoogle Cloudサービスの活用が表面的すぎて、審査基準を満たしていないと判断される。

**対策：**
- 必須要件を明示的にスライドに載せる

| 要件 | 対応 |
|---|---|
| Cloud Run | AI魔導書APIをCloud Runにデプロイ |
| Gemini API | 呪文生成・評価・GMジャッジに使用 |
| Speech-to-Text | 詠唱音声認識に使用 |
| GitHub Actions CI/CD | Push時に自動テスト・自動デプロイ |
| ログ収集 | Cloud Loggingで詠唱ログを収集 |
| 改善サイクル | ログをもとにGeminiプロンプトを改善 |

- 「ログ → 分析 → 改善 → 再デプロイ」のサイクルをアーキテクチャ図に必ず入れる
- [[01_ハッカソン要件対応]] を発表前に再確認する

---

## リスクマトリクス

| リスク | 発生確率 | 影響度 | 優先度 |
|---|---|---|---|
| 不適切表現生成 | 中 | 高 | 最優先 |
| ゲーム作り込み過剰 | 高 | 中 | 高 |
| 音声認識不安定 | 高 | 中 | 高 |
| デモが伝わらない | 中 | 高 | 高 |
| 要件とのズレ | 低 | 高 | 中 |
