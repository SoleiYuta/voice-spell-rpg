# バックエンド構成

AI Grimoire のバックエンド（AI魔導書API）を構成する主要技術の調査ノート。

---

## 1. FastAPI

### 役割

AI魔導書APIのWebフレームワーク。Unity → Cloud Run 間の HTTP リクエストを受け付け、STT・Gemini・Firestore と連携して結果を返す。

### 今回のゲームで使う理由

- Python で書けるため、Gemini SDK・librosa・Speech-to-Text SDK とシームレスに組み合わせられる
- 非同期処理（async/await）対応でレスポンスが速い
- OpenAPI ドキュメント自動生成により API 仕様書が常に最新状態を保つ
- Cloud Run との公式クイックスタートが存在し、導入コストが低い

### 主要機能

| 機能 | 内容 |
|---|---|
| ファイルアップロード | `UploadFile`（multipart/form-data）で音声 WAV を受け取る |
| リクエストバリデーション | Pydantic によるリクエスト/レスポンスの型チェック |
| 非同期処理 | `async def` + `await` で Gemini API 等の待機をブロックせずに処理 |
| 自動ドキュメント | `/docs`（Swagger UI）で API 仕様を確認可能 |
| エラーハンドリング | HTTPException で統一したエラーレスポンス |

### エンドポイント設計方針

```
POST /evaluate      - 音声ファイルを受け取り、STT + 評価スコアを返す
POST /generate-spell - プレイヤーログを受け取り、次の呪文を返す
POST /master-judge  - フロアクリアログを受け取り、次フロア設定を返す
GET  /result/{session_id} - セッション総評を返す
```

詳細は [[tech/API設計]] を参照。

### 注意点

- ファイルアップロードには `python-multipart` パッケージが必要（pip install）
- 音声ファイルサイズの上限を設定すること（デフォルト無制限は危険）
- `startup_cpu_boost` が Cloud Run で有効な場合、コールドスタートを短縮できる

### メリット / デメリット

| メリット | デメリット |
|---|---|
| Python エコシステムをそのまま使える | Node.js と比べてコンテナサイズが大きくなりやすい |
| 自動ドキュメントが便利 | 非同期の扱いに注意が必要 |
| 型安全・バリデーションが強力 | |

### 代替案

| 代替 | 理由 |
|---|---|
| Flask | シンプルだが非同期・型安全が弱い |
| Django | オーバースペック |
| Node.js (Express/Hono) | Google SDK の Python 版の方が成熟している |

### 公式ドキュメント

- FastAPI: https://fastapi.tiangolo.com/
- ファイルアップロード: https://fastapi.tiangolo.com/tutorial/request-files/
- Cloud Run + FastAPI クイックスタート: https://cloud.google.com/run/docs/quickstarts/build-and-deploy/deploy-python-fastapi-service

### ハッカソン最低限実装

- `POST /evaluate` と `POST /generate-spell` の 2 エンドポイントを作成
- UploadFile で WAV を受け取り、Speech-to-Text → Gemini へ流す

### 発展実装

- WebSocket エンドポイントでリアルタイムストリーミング認識
- レート制限ミドルウェアの追加
- 認証ミドルウェア（Firebase Auth JWT 検証）

## 2. Cloud Run

### 役割

FastAPI（AI魔導書API）をコンテナとしてデプロイするサーバーレス実行環境。ハッカソン要件の「Google Cloud アプリケーション実行プロダクト」に直接対応。

### 今回のゲームで使う理由

- サーバーレスのためインフラ管理不要
- コンテナさえ用意すれば Flask でも FastAPI でも動く
- リクエストがないときはスケールゼロ（コスト最適）
- GitHub Actions からの自動デプロイが容易

### 主要仕様

| 項目 | 内容 |
|---|---|
| タイムアウト | デフォルト 300 秒、最大 60 分（15分超はベータ） |
| リクエスト制限 | 同時リクエスト数の上限は設定可能（デフォルト 80/インスタンス） |
| コールドスタート | Python コンテナで数秒程度。`startup_cpu_boost` で短縮可能 |
| スケール | リクエスト数に応じて自動スケールアップ/ダウン |
| 最小インスタンス | `min-instances=1` でコールドスタートを回避できる（要課金） |

### 料金

| 項目 | 単価（概算） |
|---|---|
| CPU | $0.00002400 / vCPU秒 |
| メモリ | $0.00000250 / GiB秒 |
| リクエスト数 | $0.40 / 100万リクエスト |
| **無料枠** | 月180,000 vCPU秒、360,000 GiB秒、200万リクエスト |

> ハッカソン規模なら無料枠内で収まる可能性が高い。

- 公式料金: https://cloud.google.com/run/pricing

### デプロイフロー

```
GitHub main ブランチへの Push
  → GitHub Actions
    → Docker build
    → Artifact Registry へ push
    → Cloud Run へデプロイ
```

詳細は [[tech/GitHub ActionsとCI_CD]] を参照。

### 注意点

- コールドスタート時に Gemini SDK や librosa のインポートが遅い場合あり
- `startup_cpu_boost = true` を設定するとコールドスタートが短縮される
- コンテナは PORT 環境変数のポートをリッスンする必要がある（デフォルト 8080）
- secrets（APIキー等）は Secret Manager から環境変数として注入する

### メリット / デメリット

| メリット | デメリット |
|---|---|
| インフラ管理不要 | コールドスタートがある |
| スケールゼロで安い | ステートフルな処理には不向き |
| GitHub Actions との連携が簡単 | ローカルとの環境差異に注意 |

### 代替案

| 代替 | 理由 |
|---|---|
| Cloud Functions | 軽量処理向け、ファイルアップロードに弱い |
| GKE | オーバースペック |
| App Engine | 柔軟性が低い |

### 公式ドキュメント

- Cloud Run 概要: https://cloud.google.com/run
- Python 最適化: https://cloud.google.com/run/docs/tips/python
- 料金: https://cloud.google.com/run/pricing

### ハッカソン最低限実装

- `Dockerfile` を作成し、FastAPI アプリをコンテナ化
- Cloud Run に手動でデプロイ（まず動かす）
- GitHub Actions で自動デプロイ化

### 発展実装

- `min-instances=1` でコールドスタート排除
- Cloud Run の CPU/メモリを調整してパフォーマンス最適化
- リージョン選択（asia-northeast1=東京）

## 3. Firestore

### 役割

プレイヤーの詠唱ログ・セッション情報を保存するNoSQLデータベース。AIゲームマスターが参照するデータストアとして機能する。

### 今回のゲームで使う理由

- ドキュメント指向（JSON的）なデータを自然に扱える
- Python SDK がある
- Firebase/GCP と同じプロジェクトで管理できる
- リアルタイム同期は不要なのでバッチ読み書きで十分
- 無料枠が比較的大きい

### データモデル設計

```
sessions/                          ← コレクション
  {session_id}/                    ← ドキュメント
    player_id: string
    started_at: timestamp
    floors/                        ← サブコレクション
      {floor_id}/
        spell_text: string
        evaluation: {
          match_rate: float,
          volume: string,
          speed: float,
          emotion: string
        }
        gm_comment: string
        completed_at: timestamp
```

### 料金

| 操作 | 無料枠 | 超過料金 |
|---|---|---|
| 読み取り | 50,000 回/日 | $0.06 / 100,000 件 |
| 書き込み | 20,000 回/日 | $0.18 / 100,000 件 |
| 削除 | 20,000 回/日 | $0.02 / 100,000 件 |
| ストレージ | 1 GiB | $0.18 / GiB |

> ハッカソン規模なら無料枠内で十分。

- 公式料金: https://firebase.google.com/docs/firestore/pricing

### 注意点

- コレクション名・ドキュメント ID はシンプルな英数字にする
- Cloud Run から Firestore を使う場合は IAM の `roles/datastore.user` が必要
- セキュリティルールはハッカソンでは簡易設定で OK（本番では必ず締める）

### メリット / デメリット

| メリット | デメリット |
|---|---|
| JSON的データをそのまま保存可能 | 複雑なクエリ（JOIN等）は苦手 |
| 無料枠が大きい | スキーマレスなので設計を明確にしないとカオスになる |
| Python SDK が充実 | |

### 代替案

| 代替 | 理由 |
|---|---|
| Cloud SQL（PostgreSQL） | スキーマ管理が必要でハッカソンでは重い |
| Firebase Realtime Database | 古い。Firestoreの方が機能が上 |
| BigQuery | 分析向け、リアルタイムには不向き |

### 公式ドキュメント

- データモデル: https://firebase.google.com/docs/firestore/data-model
- Python SDK: https://cloud.google.com/python/docs/reference/firestore/latest
- クイックスタート: https://firebase.google.com/docs/firestore/quickstart

### ハッカソン最低限実装

- セッション開始時にドキュメント作成
- フロアクリアごとに評価ログを書き込み
- セッション終了時に全ログを読み出してリザルト生成

### 発展実装

- セキュリティルールで書き込み制限
- Cloud Logging と連携してログ可視化
- Firestore の変更をトリガーに Cloud Functions でリアルタイム処理
